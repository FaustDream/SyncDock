# 同步坞稳定性与同步策略设计

> 版本：v1.0  
> 更新时间：2026-04-06

---

## 1. 设计总原则

同步坞的稳定性设计必须遵守一个核心原则：

> **宁可跳过，也不要误改。**

因此，同步坞的自动化能力必须建立在保守和可解释的基础之上，而不能建立在隐式修复和猜测用户意图之上。

---

## 2. 首版默认同步模式

首版仅开放一种同步模式：**Safe 模式**

### Safe 模式规则

- ✅ 有本地未提交修改则跳过
- ✅ 可选地对未跟踪文件执行保护性跳过
- ✅ 先执行 `git fetch --all --prune`
- ✅ 再执行 `git pull --ff-only`
- ❌ 不自动 merge
- ❌ 不自动 rebase
- ❌ 不自动 stash
- ❌ 不自动 push
- ❌ 不自动解决冲突

该模式是同步坞首版稳定性的核心保障。

---

## 3. 仓库同步流程

对于每个仓库，采用如下流程：

```
开始
  ↓
校验路径是否存在
  ↓ (否)
标记失效 → 跳过
  ↓ (是)
校验是否为有效 Git 仓库
  ↓ (否)
标记无效 → 跳过
  ↓ (是)
读取当前分支
  ↓
检查本地工作区是否干净
  ↓ (否)
标记有改动 → 跳过
  ↓ (是)
检查 upstream 是否存在
  ↓ (否)
标记无 upstream → 跳过
  ↓ (是)
执行 `git fetch --all --prune`
  ↓ (失败)
记录失败原因 → 失败
  ↓ (成功)
比较本地与远端差异
  ↓
判断是否可快进
  ↓ (否)
标记需手动处理 → 失败
  ↓ (是)
执行 `git pull --ff-only`
  ↓ (失败)
记录失败原因 → 失败
  ↓ (成功)
更新状态 → 成功
  ↓
输出结果并写入日志
```

## 4. 跳过策略

### 4.1 必跳过场景

| 场景 | 跳过原因 | 用户提示 |
|------|----------|----------|
| 仓库目录不存在 | 无法同步不存在的仓库 | 仓库路径不存在，已跳过 |
| 非有效 Git 仓库 | 不是 Git 仓库无法同步 | 不是有效仓库，已跳过 |
| 当前分支异常 | 分支状态不正常 | 当前分支异常，已跳过 |
| 本地存在未提交修改 | 保护本地工作区 | 存在未提交修改，已跳过 |
| 当前分支未配置 upstream | 无法确定同步目标 | 未配置 upstream，已跳过 |
| 用户已禁用该仓库 | 用户主动设置 | 仓库已禁用，已跳过 |
| Git 不可用 | 环境问题 | Git 环境异常，已跳过 |

### 4.2 可配置跳过场景

| 场景 | 默认行为 | 配置项 |
|------|----------|--------|
| 存在未跟踪文件 | 跳过 | `skipUntrackedFiles` |
| 当前处于 detached HEAD | 跳过 | 固定跳过 |
| 当前处于 rebase/merge 中 | 跳过 | 固定跳过 |

### 4.3 跳过说明

**跳过应被视为受保护状态，而非系统错误。**

用户需要明确知道：
- 为什么跳过
- 跳过是保护行为
- 如何解决（如果需要）

## 5. 状态机设计

同步执行过程采用有限状态机：

### 5.1 状态定义

| 状态 | 说明 | 可转换状态 |
|------|------|------------|
| Idle | 空闲，未开始 | Checking |
| Checking | 检查仓库状态 | Fetching, Skipped, Failed |
| Fetching | 执行 git fetch | Comparing, Failed |
| Comparing | 比较差异 | Pulling, Failed |
| Pulling | 执行 git pull | Success, Failed |
| Success | 同步成功 | Idle |
| Skipped | 跳过同步 | Idle |
| Failed | 同步失败 | Idle |
| Cancelled | 用户取消 | Idle |

### 5.2 状态转换规则

```
Idle → Checking (开始同步)
Checking → Fetching (状态检查通过)
Checking → Skipped (状态检查不通过)
Checking → Failed (检查失败)
Fetching → Comparing (fetch 成功)
Fetching → Failed (fetch 失败)
Comparing → Pulling (可快进)
Comparing → Failed (不可快进)
Pulling → Success (pull 成功)
Pulling → Failed (pull 失败)
Pulling → Cancelled (用户取消)
Success/Skipped/Failed/Cancelled → Idle (任务结束)
```

### 5.3 状态机优势

- UI 展示清晰
- 逻辑可维护
- 日志结构统一
- 后续便于扩展重试机制

## 6. 错误分类

### 6.1 环境类错误

| 错误 | 错误码 | 说明 |
|------|--------|------|
| Git 未安装 | SD-ENV-001 | 系统 PATH 中未找到 git |
| Git 不可执行 | SD-ENV-002 | git 命令无法执行 |
| Git 版本过低 | SD-ENV-003 | 版本低于最低要求 |
| 配置目录不可写 | SD-ENV-004 | 无法写入配置目录 |

### 6.2 仓库类错误

| 错误 | 错误码 | 说明 |
|------|--------|------|
| 路径不存在 | SD-FS-001 | 仓库目录不存在 |
| 不是有效仓库 | SD-REPO-001 | 缺少 .git 目录 |
| 仓库已损坏 | SD-REPO-002 | Git 仓库结构异常 |
| 未配置 upstream | SD-REPO-003 | 当前分支无上游 |
| 存在未提交修改 | SD-REPO-004 | 工作区有改动 |
| 存在未跟踪文件 | SD-REPO-005 | 有未跟踪文件 |
| detached HEAD | SD-REPO-006 | HEAD 游离 |
| rebase/merge 中 | SD-REPO-007 | 处于中间状态 |

### 6.3 同步类错误

| 错误 | 错误码 | 说明 |
|------|--------|------|
| 状态读取失败 | SD-SYNC-001 | 无法获取仓库状态 |
| fetch 失败 | SD-SYNC-002 | 无法获取远端更新 |
| 无法快进 | SD-SYNC-003 | 分支无法 fast-forward |
| 同步超时 | SD-SYNC-004 | 命令执行超时 |
| 结果写入失败 | SD-SYNC-005 | 无法保存同步结果 |
| 同步被取消 | SD-SYNC-006 | 用户取消任务 |

### 6.4 网络与鉴权类错误

| 错误 | 错误码 | 说明 |
|------|--------|------|
| SSH 鉴权失败 | SD-AUTH-001 | SSH key 或 agent 问题 |
| HTTPS 凭证失败 | SD-AUTH-002 | 凭证无效或过期 |
| 访问被拒绝 | SD-AUTH-003 | 无权限访问远端 |
| 网络连接失败 | SD-NET-001 | 无法连接远端服务 |
| 网络超时 | SD-NET-002 | 远端响应超时 |

## 7. 日志设计

### 7.1 用户态日志

面向界面展示，内容应简洁：

| 字段 | 说明 | 示例 |
|------|------|------|
| 仓库名 | 仓库标识 | docs-repo |
| 当前步骤 | 执行阶段 | Fetching |
| 结果 | 成功/跳过/失败 | Success |
| 原因摘要 | 简短说明 | 同步完成 |

### 7.2 调试日志

面向排错，保留原始命令信息：

| 字段 | 说明 | 示例 |
|------|------|------|
| 时间戳 | 执行时间 | 2026-04-06 14:30:00 |
| 仓库名 | 仓库标识 | docs-repo |
| 命令 | Git 命令 | git fetch --all --prune |
| 参数 | 命令参数 | --all --prune |
| 返回码 | Exit code | 0 |
| stdout | 标准输出 | ... |
| stderr | 错误输出 | ... |
| 执行耗时 | Duration | 1.2s |

### 7.3 日志文件

- **位置**: `{configDir}/logs/`
- **命名**: `task_YYYYMMDD_HHMMSS.log`
- **格式**: JSON Lines（每行一个 JSON 对象）
- **清理**: 按配置天数自动清理（默认 30 天）

## 8. 重试策略

### 8.1 可自动重试

| 场景 | 说明 | 重试次数 |
|------|------|----------|
| 短时网络异常 | 临时网络问题 | 最多 2 次 |
| fetch 超时 | 网络慢导致超时 | 最多 1 次 |
| 临时锁文件 | Git 锁文件冲突 | 最多 1 次 |

### 8.2 不自动重试

| 场景 | 说明 | 原因 |
|------|------|------|
| 本地脏工作区 | 有未提交修改 | 需要用户处理 |
| 鉴权失败 | SSH/HTTPS 问题 | 需要用户配置 |
| upstream 缺失 | 未配置上游 | 需要用户设置 |
| fast-forward 失败 | 分支分叉 | 需要手动处理 |
| 冲突错误 | 合并冲突 | 需要手动解决 |

### 8.3 重试原则

> **只有重复执行大概率能成功的问题，才进入自动重试范围。**

## 9. 隔离策略

批量同步中，每个仓库必须视为独立任务单元：

### 9.1 隔离要求

- ✅ 独立执行上下文
- ✅ 独立结果记录
- ✅ 独立错误捕获
- ✅ 单仓库失败不影响其他仓库

### 9.2 隔离实现

```rust
for repo in repositories {
    match sync_repository(repo) {
        Ok(result) => record_success(result),
        Err(error) => record_failure(error),
    }
    // 继续处理下一个仓库，不中断
}
```

**这点是整个产品可长期使用的基础。**

## 10. UI 与执行隔离

同步逻辑不得直接阻塞 UI。

### 10.1 架构要求

- UI 线程只负责展示
- 后台任务负责执行 Git 命令
- 结果通过事件流更新到界面
- 日志实时写盘，避免崩溃丢失

### 10.2 实现方式

```rust
// 后台线程执行
std::thread::spawn(move || {
    let result = sync_all_repositories();
    // 通过事件发送结果
    window.emit("sync-progress", result);
});
```

### 10.3 取消支持

- 任务执行期间监听取消信号
- 在仓库粒度检查取消标志
- 当前仓库完成后停止后续仓库
- 已完成的结果正常记录

## 11. 一致性定义

同步坞的一致性并不等于"所有仓库都同步成功"。

### 11.1 一致性维度

同步坞的一致性应定义为：

- **状态识别一致**: 同一仓库状态判断逻辑稳定
- **行为策略一致**: 同样场景下跳过/失败行为一致
- **结果表达一致**: 同类错误使用相同文案
- **错误解释一致**: 错误码与说明对应关系固定

### 11.2 避免不一致

- ❌ 同一错误在不同页面显示不同文案
- ❌ 同一场景有时跳过有时失败
- ❌ 状态刷新前后结果不一致
- ❌ 日志与界面信息不一致

## 12. 首版默认规则清单

| 编号 | 规则 | 说明 |
|------|------|------|
| 1 | 同步前强制检查状态 | 确保仓库可同步 |
| 2 | 有本地修改则跳过 | 保护工作区 |
| 3 | 仅允许安全快进拉取 | 不做危险操作 |
| 4 | 不做隐式历史修改 | 不改变提交历史 |
| 5 | 单仓库失败不影响整体任务 | 隔离策略 |
| 6 | 结果必须可追踪 | 日志记录完整 |
| 7 | 不自动提交、不自动推送、不自动变基 | 保守原则 |
