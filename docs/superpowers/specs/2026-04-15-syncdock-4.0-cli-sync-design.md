# SyncDock 4.0 CLI 多仓库同步器设计

## 1. 背景

SyncDock 的原始目标是解决两台电脑之间的多 Git 仓库快速同步问题。过去的 2.0 桌面版和 3.0 网页版都逐步偏离了这个核心目标，功能变得过多，维护成本高，但核心同步效率并没有因此明显提升。

本次 4.0 方案回归最小可用产品思路，只聚焦一个问题：

- 在当前电脑上，快速同步多个本地 Git 仓库到最新远端状态

4.0 不再追求复杂平台化能力，而是优先满足以下目标：

- 批量同步多个仓库
- 支持 Windows 本地直接使用
- 支持通过计划任务定时执行
- 运行内存尽量小
- 执行完成后自动退出
- 日志直白、易懂

## 2. 目标与非目标

### 2.1 目标

SyncDock 4.0 需要实现以下能力：

- 通过 `bat` 双击启动
- 进入简单数字菜单的交互式命令行界面
- 支持同步全部仓库
- 支持同步指定仓库
- 支持查看仓库当前状态
- 支持查看最近一次日志摘要
- 支持重新加载配置
- 支持静默模式执行全部同步后退出
- 支持被 Windows 计划任务调用

### 2.2 非目标

以下内容明确不纳入 4.0 范围：

- 网页版
- 复杂桌面 GUI
- 自动提交本地修改
- 自动推送远端
- 云端配置同步
- 复杂任务中心
- 统计看板
- 自动修复 Git 异常状态

## 3. 总体方案

4.0 采用 `Python + bat` 的本地执行方案。

系统分为四层：

- 启动层：`run-sync.bat` 与 `run-sync-silent.bat`
- 交互层：数字菜单式命令行界面
- 内核层：Python 同步引擎
- 配置与日志层：JSON 配置文件与本地日志文件

整体运行流程如下：

1. 用户双击 `run-sync.bat`，或计划任务调用 `run-sync-silent.bat`
2. `bat` 启动 Python 程序
3. Python 加载配置
4. 执行菜单动作或静默同步动作
5. 输出屏幕结果并写入日志
6. 菜单模式返回主菜单，静默模式直接退出

## 4. 技术选择

### 4.1 后端语言

4.0 使用 Python 作为同步内核语言。

选择原因：

- 适合快速实现本地工具
- 适合调用 Git 命令并处理结果
- 易于维护和迭代
- 适合与 `bat` 配合
- 适合先做稳定的轻量工具，而不是重新搭建复杂桌面架构

### 4.2 界面形式

4.0 不使用复杂前端框架，而采用简单数字菜单反复选择的交互式命令行界面。

交互原则：

- 界面只在用户主动选择退出时关闭
- 每次操作完成后返回主菜单
- 菜单简单、动作明确
- 文案直白，不堆砌 Git 术语

## 5. 目录结构

建议目录结构如下：

```text
SyncDock/
  run-sync.bat
  run-sync-silent.bat
  requirements.txt
  README.md
  config/
    repositories.json
    settings.json
  logs/
  syncdock/
    main.py
    menu.py
    sync_engine.py
    repo_checker.py
    log_service.py
    config_service.py
```

各部分职责：

- `run-sync.bat`
  手动启动入口，进入交互菜单
- `run-sync-silent.bat`
  静默启动入口，用于计划任务
- `config/repositories.json`
  维护仓库列表
- `config/settings.json`
  维护运行策略
- `logs/`
  存放运行日志
- `syncdock/main.py`
  主程序入口
- `syncdock/menu.py`
  菜单与用户交互
- `syncdock/sync_engine.py`
  批量同步核心
- `syncdock/repo_checker.py`
  仓库状态检查
- `syncdock/log_service.py`
  日志输出和摘要
- `syncdock/config_service.py`
  配置读取与校验

## 6. 配置设计

### 6.1 仓库配置

`repositories.json` 仅维护仓库清单。

示例：

```json
{
  "repositories": [
    {
      "name": "SyncDock",
      "path": "E:\\gitHub\\SyncDock",
      "enabled": true
    },
    {
      "name": "batchfetch",
      "path": "E:\\gitHub\\batchfetch",
      "enabled": true
    }
  ]
}
```

字段说明：

- `name`
  菜单和日志中的展示名
- `path`
  本地仓库绝对路径
- `enabled`
  是否参与默认同步

### 6.2 运行配置

`settings.json` 仅维护运行策略。

示例：

```json
{
  "concurrent_limit": 3,
  "command_timeout_seconds": 120,
  "skip_uncommitted_changes": true,
  "skip_untracked_files": false,
  "log_retention_days": 30
}
```

字段说明：

- `concurrent_limit`
  最大并发仓库数
- `command_timeout_seconds`
  单个 Git 命令超时时间
- `skip_uncommitted_changes`
  遇到未提交修改时是否跳过
- `skip_untracked_files`
  遇到未跟踪文件时是否跳过
- `log_retention_days`
  日志保留天数

4.0 先使用 JSON，不使用 YAML，原因是结构简单、易读、Python 处理成本更低。

## 7. 菜单设计

主菜单固定为简单数字菜单：

```text
SyncDock 4.0

1. 同步全部仓库
2. 同步指定仓库
3. 查看仓库状态
4. 查看最近日志
5. 重新加载配置
0. 退出
```

### 7.1 同步全部仓库

- 加载全部启用仓库
- 执行批量同步
- 显示逐仓库结果
- 显示汇总摘要
- 提示按回车返回主菜单

### 7.2 同步指定仓库

- 列出启用仓库和编号
- 用户输入编号
- 仅同步所选仓库
- 显示结果并返回主菜单

### 7.3 查看仓库状态

- 不执行 `pull`
- 仅做状态检查
- 输出每个仓库当前状态

### 7.4 查看最近日志

- 展示最近一次运行摘要
- 展示最近若干条日志明细

### 7.5 重新加载配置

- 重新读取两个 JSON 配置文件
- 输出成功或失败结果

### 7.6 退出

- 正常退出程序

## 8. 同步内核设计

### 8.1 同步前提

4.0 的同步前提如下：

- 另一台电脑上的修改已经完成 `commit + push`
- 当前电脑只负责拉取远端代码到本地
- 4.0 不负责自动提交，也不负责自动推送

### 8.2 单仓库同步流程

单个仓库按照以下顺序处理：

1. 检查路径是否存在
2. 检查是否为有效 Git 仓库
3. 检查是否处于 `detached HEAD`
4. 检查是否存在未提交修改
5. 检查是否存在未跟踪文件
6. 检查是否正在 `merge/rebase/cherry-pick`
7. 检查当前分支是否已配置 `upstream`
8. 执行 `git fetch --all --prune`
9. 判断本地与远端差异
10. 如可安全更新，则执行 `git pull --ff-only`
11. 写入结果

### 8.3 同步策略

4.0 使用保守同步策略：能安全拉取就拉取，不能安全拉取就跳过。

默认策略如下：

- 有未提交修改：跳过
- `detached HEAD`：跳过
- 正在 `merge/rebase/cherry-pick`：跳过
- 未配置 `upstream`：跳过
- 需要非快进合并：跳过并记失败或警告
- Git 超时或网络失败：记录失败，继续下一个仓库

该策略的目标是避免工具擅自修改复杂仓库状态。

## 9. 结果模型

4.0 将同步结果固定为五类：

- `UPDATED`
  已成功拉取最新代码
- `UP_TO_DATE`
  本地已经是最新
- `SKIPPED`
  当前仓库状态不适合同步，因此跳过
- `FAILED`
  执行失败，例如网络、认证、超时或 Git 错误
- `INVALID`
  路径不存在或不是有效 Git 仓库

这些结果将用于：

- 屏幕输出
- 日志记录
- 汇总统计

## 10. 日志与文案设计

### 10.1 文案原则

4.0 的日志文案遵循以下规则：

- 优先使用人话
- 尽量避免直接暴露 Git 底层术语
- 屏幕输出要简单直白
- 详细技术信息仅进入日志文件

### 10.2 屏幕输出示例

示例文案：

- `已拉取最新代码`
- `已经是最新`
- `已跳过，有未提交修改`
- `已跳过，当前不在分支上`
- `已跳过，当前分支未设置同步目标`
- `同步失败，网络连接异常`
- `仓库无效，路径不存在`

示例：

```text
[SyncDock] SyncDock: 已拉取最新代码
[SyncDock] batchfetch: 已经是最新
[SyncDock] repo-a: 已跳过，有未提交修改
[SyncDock] repo-b: 同步失败，网络连接异常
```

### 10.3 摘要输出

同步全部仓库结束后输出简短摘要：

```text
同步完成

总仓库数：8
已同步：3
无需同步：2
已跳过：2
失败：1
无效：0
```

### 10.4 日志文件格式

日志文件可保留稍微详细的信息，便于排查：

```text
2026-04-15 22:31:08 | repo-a | FAILED | git fetch timeout after 120 seconds
```

即：

- 屏幕日志面向日常使用
- 文件日志面向排错

## 11. 静默模式与计划任务

4.0 提供静默模式，用于计划任务自动执行。

静默模式要求：

- 不进入交互菜单
- 自动执行“同步全部仓库”
- 仅写必要控制台输出和日志
- 执行后自动退出
- 返回明确退出码

`run-sync-silent.bat` 用于该场景。

后续 Windows 计划任务可直接调用该入口。

## 12. 与现有版本的关系

### 12.1 版本定位

新方案版本定位为：

- `SyncDock 4.0`

### 12.2 分支策略

分支策略建议如下：

- 现有 2.0 保留为 `syncdock2.0`
- `main` 转为 4.0 新方案主线

这样可以同时保留旧桌面版资产和新极简主线。

### 12.3 与 batchfetch 的关系

4.0 参考 `batchfetch` 的批量仓库处理思路，但不直接抽取其代码。

原因：

- 许可证风险高，`batchfetch` 使用 GPLv3
- 当前目标是做轻量、可控的本地工具
- 4.0 更适合独立实现自己的极简同步内核

## 13. 风险与边界

4.0 需要关注以下风险：

- 用户本地仓库状态复杂时，跳过策略需要明确且稳定
- Git 认证、代理、网络问题会直接影响同步成功率
- 计划任务环境与用户手动运行环境可能不同
- 如果用户希望未来支持自动修复或自动推送，需要单独规划，不应混入 4.0 首版

控制原则：

- 先保证安全
- 再保证可用
- 最后考虑扩展

## 14. 第一阶段交付范围

4.0 第一阶段交付建议仅包含：

- 项目基础目录结构
- 配置读取与校验
- 主菜单
- 同步全部仓库
- 同步指定仓库
- 查看仓库状态
- 最近日志查看
- 静默模式
- 简单日志与摘要输出

第一阶段不包含：

- 配置文件可视化编辑
- 分组同步
- 托盘常驻
- 安装包
- 自动计划任务创建

## 15. 结论

SyncDock 4.0 应回归极简路线，作为一个本地、轻量、可定时执行的多仓库同步工具存在。其核心价值不在于提供复杂管理平台，而在于帮助用户快速、安全地把多个本地 Git 仓库同步到最新状态。

4.0 的最佳起点是：

- Python 同步内核
- `bat` 启动入口
- 简单数字菜单命令行界面
- 保守同步策略
- 直白的人话日志

该方案范围清晰、实现成本低、适合快速落地，也最符合项目原始目标。
