# SyncDock 本地网页化重构设计

日期：2026-04-10
状态：待用户审阅

## 目标

SyncDock 从 Tauri 优先的桌面应用，重构为面向个人和少数技术用户的本地网页工具。主界面运行在浏览器中，本地服务保留普通网页无法完成的能力：读写本地配置、检查 Git 仓库、执行同步任务、保存日志，并且数据不依赖浏览器缓存。

本次重构也同步收敛产品界面：仓库管理合并到总览页，任务日志中心移除，设置页精简，前端从 React 改为 Vue 3。

## 产品形态

目标架构：

```text
Vue 3 Web UI -> HTTP/WebSocket API -> Rust 本地服务 -> 本地 JSON / Git / 文件系统
```

SyncDock 不做云端服务，不增加账户和登录系统。用户启动本地进程后，在浏览器中使用。条件允许时，本地服务自动打开浏览器。

## 目标用户

- 主要用户：项目作者本人。
- 次要用户：少数能接受本地工具和命令行的技术用户。

因此首版不追求商业软件级安装体验，也不做云同步、多用户协作和非技术用户引导。

## 运行方式

本地服务同时提供 Web UI 和 API。

开发期启动方式：

```powershell
syncdock serve
```

默认浏览器地址：

```text
http://127.0.0.1:<port>
```

运行要求：

- 默认只监听 `127.0.0.1`。
- 优先使用稳定默认端口。
- 默认端口被占用时，自动选择其他本地端口并打开正确地址。
- 在终端输出访问地址。
- 默认自动打开浏览器，允许通过参数关闭。
- 服务持续运行，直到用户主动停止。

后续可按平台补充轻量启动方式：

- Windows：`.exe` 或 `.bat`。
- macOS：可执行文件或 `.command`。
- Linux：可执行文件或 shell 脚本。

## 本地数据

数据必须存在浏览器之外，避免用户清理浏览器缓存后丢失配置。

默认数据目录：

```text
~/.syncdock/
```

默认结构：

```text
~/.syncdock/
  config.json
  repositories.json
  tasks.json
  logs/
  backups/
  crash/
```

设置页保留“修改配置目录”能力。用户切换配置目录时，迁移已有设置、仓库记录、任务记录、备份、崩溃文件，以及默认日志目录中的日志。

尽量复用现有 Rust 存储能力：

- 默认存储目录
- 自定义存储目录
- JSON 设置
- JSON 仓库记录
- JSON 任务记录
- 日志目录诊断
- 配置导入导出

## API 设计

原有 Tauri `invoke` 边界改成本地 HTTP API，任务进度后续可接 WebSocket。

首批 HTTP API：

```text
GET    /api/snapshot
GET    /api/settings
PUT    /api/settings
PUT    /api/storage-directory

GET    /api/repositories
POST   /api/repositories
PUT    /api/repositories/:id
DELETE /api/repositories/:id

POST   /api/repositories/refresh
POST   /api/repositories/sync
POST   /api/repositories/force-sync

GET    /api/tasks
GET    /api/tasks/:id/log
POST   /api/tasks/cancel

GET    /api/logs/repositories
GET    /api/logs/repositories/:repoId
POST   /api/logs/cleanup

POST   /api/config/export
POST   /api/config/import/preview
POST   /api/config/import
```

任务进度第一阶段可以通过 `/api/snapshot` 轮询实现。WebSocket 等 HTTP 迁移稳定后再加入。

## 本地安全

本地服务默认只服务本机。

要求：

- 默认绑定 `127.0.0.1`，不绑定 `0.0.0.0`，除非用户显式开启。
- 不提供任意文件读写 API。
- 文件操作只允许发生在明确流程中：仓库路径、配置导入导出、日志导出、配置目录迁移。
- 如需要防止其他本地网页误调用 API，启动时生成本地 session token。
- 对无效路径、权限失败、Git 缺失、端口冲突给出结构化错误。

## 前端重构

前端从 React 改为 Vue 3。

目标技术栈：

- Vue 3
- TypeScript
- Vite
- Pinia 或 Vue composables 管理共享状态
- 仅在需要 URL 路由状态时使用 Vue Router

前端不能直接依赖 Tauri API。所有本地能力通过 API client 访问本地 HTTP 服务。

## 视觉风格

采用用户指定的 Cal.com 风格方向：干净、中性、面向开发者、简洁直接、功能密度适中。

SyncDock 视觉约束：

- 以白色、近白、黑色、灰色为主，使用一个克制的强调色。
- 使用顶部导航，不使用左侧导航。
- 优先表格、紧凑筛选、清晰空状态、直接操作。
- 不使用装饰性渐变、大型 hero、光斑背景、营销式文案。
- 控件圆角保持克制，避免卡片套卡片，列表和表格尺寸稳定。
- 文案只描述用户要做的事，不解释界面本身。

## 导航

移除左侧功能导航。

顶部导航仅保留：

- 总览
- 任务
- 设置

移除独立的“仓库”页面。仓库相关能力合并进“总览”。

## 总览页

总览页成为主工作台。

页面调整：

- 合并原“总览”和“仓库”功能。
- 原“数据状态”改为“仓库列表”。
- 移除“运行摘要”。
- “运行摘要”位置改为“日志”。
- 移除原仓库页中的“工作区”和“清单”页签。
- 仓库分组、仓库列表、筛选、同步操作直接放在总览页。
- 仓库日志放在总览页。
- 删除仓库列表下方提示词：`仅展示名称、分支、状态与最近同步时间。`

仓库列表行为：

- 展示仓库名称、分支、状态、最近同步时间、分组、归属和关键操作。
- 其他作者的仓库默认排序在最下面。
- 其他作者的仓库默认使用强制更新。
- 强制更新必须支持选择文件忽略规则，避免覆盖用户希望保留的文件。

分组和归属：

- 所有分组都显示仓库数量。
- 没有仓库的分组显示 `0`。
- 分组选择必须是下拉框，同时支持直接新增分组。
- 仓库归属使用同类“下拉选择 + 直接新增”的交互。

筛选区：

- `全部分组` 和 `全部状态` 控件宽度缩小到当前约三分之一。
- 搜索框占用筛选控件缩小后释放的空间。

## 任务页

保留任务概览和任务历史。

移除：

- 任务日志中心。

任务详情仍可查看单个任务日志，但不再提供独立的任务日志中心页面或页签。

## 设置页

移除版本和更新相关 UI：

- 最新版本
- 发布时间
- 检查更新按钮
- 版本号

移除“应用信息”标题和不必要的区域包装。将以下环境状态内容放到设置页下方合适位置：

- 日志文件数
- 占用空间
- Git 说明

移除“常规”中的这些设置及相关代码：

- 默认启动页
- 界面主题
- 窗口关闭行为
- 启动时自动刷新状态
- 语言

如果后端仍需要启动时自动刷新，可以保留默认开启行为，但不作为用户可配置项展示。

设置页保留重点：

- 配置目录
- 日志目录或日志诊断
- 仍有必要的同步设置
- 导入导出
- 本地环境状态

## 仓库归属与同步规则

仓库归属继续作为核心字段。

默认同步行为：

- 自己的仓库默认普通同步。
- 其他作者的仓库默认强制更新。
- 其他作者的仓库默认排在列表底部。

强制更新保护：

- 用户可配置强制更新时忽略的文件或匹配规则。
- 忽略规则放在仓库同步设置或仓库编辑弹窗附近。
- UI 需要明确说明被忽略文件会在强制更新时保留。
- 后端必须在执行覆盖性操作前应用忽略规则。

## 数据迁移

现有 SyncDock 数据应继续可用。

迁移要求：

- 新本地服务应读取现有 `config.json`、`repositories.json`、`tasks.json` 和日志。
- 如果为了强制更新忽略规则或 Vue UI 状态新增字段，需要提供版本化默认值。
- 用户不应因为迁移而重新录入仓库。

## 错误处理

保留现有结构化错误模型：

- code
- level
- title
- message
- detail
- action
- retryable

HTTP API 错误响应也使用该模型，保证前端提示质量不低于当前桌面版。

重点错误场景：

- Git 未安装或不可用。
- 仓库路径不存在。
- 配置目录不可写。
- 日志目录不可写。
- 端口占用。
- 强制更新被未忽略的本地改动阻止。
- 配置导入结构不匹配。

## 测试策略

后端：

- 存储路径解析和迁移单元测试。
- 仓库按归属排序单元测试。
- 强制更新忽略规则匹配单元测试。
- snapshot、settings、repositories、tasks、logs API 测试。

前端：

- 顶部导航、总览仓库列表、可新增下拉框、筛选区、设置删减项的组件测试。
- API client mock 测试。
- 浏览器冒烟测试：启动服务、打开总览、加载仓库、执行刷新、查看日志。

迁移：

- 使用当前 v2 JSON 数据做 fixture 测试。
- 验证旧数据加载后能得到新增字段默认值。

## 实施计划要点

后续实施计划应拆成这些工作流：

1. 新增 Rust 本地 HTTP 服务入口，复用现有 storage、git、sync、models、errors 模块。
2. 将 Tauri command 能力迁移为 HTTP API。
3. 用 Vue 3 重建前端，并建立本地 API client。
4. 顶部导航改为：总览、任务、设置。
5. 将仓库页能力合并进总览，移除独立仓库页。
6. 实现分组和归属的“下拉选择 + 直接新增”。
7. 实现其他作者仓库排序到底部、默认强制更新。
8. 实现强制更新忽略规则。
9. 移除任务日志中心。
10. 精简设置页并删除无用设置代码。
11. 应用 Cal.com 风格视觉方向。
12. 增加迁移和验证测试。

## 不做范围

- 云端账号。
- 登录系统。
- 远程服务端保存用户数据。
- 多用户协作。
- 将纯浏览器本地文件访问作为主架构。
- 首版完成所有平台的商业级安装包体验。

## 待实施阶段确认

- Rust HTTP 框架默认倾向 Axum，但实施计划阶段再最终确认。
- WebSocket 是否进入首版，取决于轮询方案是否满足任务进度体验。
- Web 模式稳定后，再决定是否保留 Tauri 作为可选启动器。
